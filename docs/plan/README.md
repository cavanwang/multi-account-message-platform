## 1. 为什么按这个顺序

```
切片0 地基 ──► 切片1 网关模拟器 ──► 切片2 账号状态机 ──► 切片3 出站+事件消费
                                                              │
                                                              ▼
切片4 建群/时间线/WS ──► 切片5 Agent模拟器 + A5 + 序列 + 前端
```

- **切片 0 先做**：迁移、错误契约、鉴权是所有端点的横切关注点，晚做要回头改所有接口。
- **切片 1 紧跟**：网关模拟器是 S1–S8 全部验收场景的驱动器，且"故障保真度"最难返工。
- **切片 2/3 是核心**：INV-1/2/4/5 全落在这两块；A5 与 B1 都建立在"能可靠发一条消息、能可靠收一条事件"之上。
- **切片 5 里 Agent 模拟器必须先于 A5**：没有坏行为的模拟器，A5 的协议错误分支无法验证。

## 4. 时间不够时的砍法

48 小时硬约束，按此顺序保留：

1. 切片 0–3 全做（A 组核心，占分最重）。
2. 切片 4 全做。
3. 切片 5 内按 **A5 → 前端页面 2/3/5 → B1 → B2/B3 → B4 → C 组** 的顺序做，做到哪算哪。
4. 前端页面 1 必须先有（登录是所有页面的入口），页面 4 可退化为"JSON 视图"。

## 5. 全局约定（所有切片共用）

- 单文件 < 50KB，**不超过 1000 行**；按 `domain / repos / services / http / workers` 分层。
- 不用 `any` / `@ts-ignore`；数据库改动一律 migration。
- 不提交 `.env`、密钥、`media/`。
- 每切片：先读相关文档 → 出计划 → **收到 `codecode` 后编码** → typecheck → commit。
- 测试脚本跑在宿主机，只通过 HTTP 调用容器服务。

## 6. 贯穿全局的不变量（实现时的自检锚点）

| 编号 | 不变量 | 主要落点 |
|---|---|---|
| INV-1 | 崩溃重启后不出现"网关发了、库里没记" | 切片 3 outbox 先落库 |
| INV-2 | 同一出站消息不重复发 | 切片 3 `client_msg_id` + `generation` |
| INV-3 | 已生效的工具调用不重放、不记失败 | 切片 5 `pending_execution` + 幂等键 |
| INV-4 | 停机/断流期间的事件恢复后都要处理 | 切片 3 `events_inbox` + `events_cursor` |
| INV-5 | 推给前端的事件对应已持久化的状态 | 切片 3/4 `web_events` 事务内插入 |
| INV-6 | 状态变更与其后果原子 | 切片 2 终态事务 |
| INV-7 | 同群至多一个 running 的 run | 切片 2/5 partial unique index |
